# Bounded Page comment replies

The current April16,2026 [Pages comments guide](https://developers.facebook.com/documentation/pages-api/comments-mentions) links the [v26common Object/comments Publishing reference](https://developers.facebook.com/docs/graph-api/reference/v26.0/object/comments#publish). That common reference explicitly lists Comment replies, New Page Experience Comment/PostComment support, Page token with MODERATE and pages_manage_engagement, POST/{object-id}/comments message and returned Comment ID. The generated Comment/comments page still declares Creating unavailable. This implementation follows the explicitly linked common publishing contract and records the contradiction; it does not claim those two references agree.

`pages_reply_comment` accepts plain message text up to2000UTF8bytes, no mentions, URLs, attachments or caller author fields. The selected Page credential, current conservative permission dependencies, exact client/app grants and Page-only literal MODERATE task must authorize the entire registered ancestry. COMMENT grants never inherit Page tasks.

Before the single approved POST, fixed current reads verify the registered target and each COMMENT parent (up to8levels), target can_comment===true, actual published Post.from.id matching the registered Page, and top-level membership in the first100 IDs from that exact Post/comments edge. A missing firstpage membership is HOLD, not an assertion that the comment is absent. No paging URL is followed. The target may be authored by a customer; Page ownership is proved through the post, not by demanding that the customer comment's author is the Page.

The current Comment reference defines id as an opaque Comment-ID token and parent as the parent COMMENT for replies, not the parent post. Top-level parent is therefore required absent and post association is proved using the edge membership read. Returned IDs use a conservative local numeric/underscore bound of100characters; no ownership is inferred by parsing that token. The exact approved registered COMMENT parent supplies authority for the newly registered reply. The new child grant has tasks[], and current Page task authority remains scoped to its Page ancestor.

Final current authorization is checked after preflight. Unknown provider outcomes retain the consumed approval and require reconciliation; there is no automatic retry. Synthetic native journeys exercise actual human approval, fixed provider reads, one POST and atomic child registration plus foreign Page/parent, false can_comment, missing membership and mid-preflight revocation denials. They are not live Meta app acceptance or proof that a particular client comment is reply-eligible.
