# CRM Conversion Leads contract and runtime handoff

Primary Meta payload and developer implementation guides are both updated June28,2026:

- https://developers.facebook.com/documentation/ads-commerce/conversions-api/conversion-leads-integration/payload-specification
- https://developers.facebook.com/documentation/ads-commerce/conversions-api/conversion-leads-integration/crm-integration/3-implementing-the-crm-integration
- Official pinned SDK UserData declares lead_id as a string and passes it through rather than hashing: https://github.com/facebook/facebook-python-business-sdk/blob/efd8423a2e595ea8d4c04eb824ce113f2f1d68cd/facebook_business/adobjects/serverside/user_data.py

This is a separate Instant Forms Conversion Leads integration, not the ordinary website event payload. CRM stages are advertiser-defined free-form names. InitialLead/QualifiedLead/ConvertedLead are a proposed immutable local funnel pack, never claimed as Meta standard event enums. The server requires actual CRM history, including every configured prior stage, rather than manufacturing qualified/converted outcomes from a snapshot.

The verified endpoint is POST graph.facebook.com/API_VERSION/PIXEL_ID/events. Meta's guide generates a dedicated CRM Pixel token in Events Manager. Required fields are actual stage event_name/time, system_generated action_source, custom_data event_source=crm and actual lead_event_source CRM name, plus at least one matching parameter. The local first slice retains exact actual15–17-digit lead_id as a string and hashes any email/phone; raw identifiers never enter MCP output/audit/journal. Events must occur strictly after actual lead generation and within seven days; no timestamp rewriting/backfill shortcut. API acceptance does not establish CRM recognition, optimization readiness or a business outcome.

`crm-signals.ts` exports scoped trusted-source evidence and an opaque prepared event. The immutable deployment funnel selects names and CRM tool. Evidence must bind exact tenant/client/app/Pixel/source/consent, actual Instant Form lead, generation timestamp, Page/form/ad/account closure, current registry digest and a five-minute actual lead observation. The production resolver must derive leadBinding internally from current authorized registry/provider proof; external CRM source JSON must never self-certify that structure. Every dispatch re-resolves source/consent/binding and revalidates the active execution permit and selected credential/privacy state. The existing website event schema and semantics remain unchanged.

`crm-stage-journal.ts` exports Memory and Firestore atomic journals. Claim requires all configured earlier stage checkpoints ACCEPTED, exact same lead HMAC/funnel/generation and strict event chronology. ATTEMPTED and UNKNOWN never auto-resend or advance. ACCEPTED means exactly one provider-accepted event receipt, not delivered/optimized/true outcome. A late authorization/expiry change after provider egress leaves the attempt held for reconciliation rather than inventing success.

Privacy classification is KEEP_SHARED_CLIENT_CUSTOMER_SOURCE: pseudonymous journal data is still personal data, not anonymous. Agency-operator withdrawal must stop that credential's execution; it does not infer which customer source to erase. Trusted actual customer-consent revocation uses an opaque verifier-bound proof and a terminal scope/lead tombstone and permanent minimal no-resend barrier. Authenticated client/customer purge removes stage/audit metadata while retaining a permanent minimal HMAC-based revocation/no-resend safety barrier, so purge or a changed funnel cannot open a resend path. No MCP raw-consent setter exists.

Firestore collections platform_crm_stage_journal, platform_crm_stage_audit and platform_crm_consent_revocations require TTL on expireTime. Retention90days exceeds the permitted7-day raw-event lifetime; TTL alone is not privacy deletion. Customer purge uses a bounded scopeHash/leadHash composite query (up to100 records); its index must be installed at the separately authorized release stage. More records HOLD for reconciliation. Detailed observations expire after ninety days, but permanent minimal platform_crm_no_resend stage barriers prevent a fresh later event_time from recreating an attempted, UNKNOWN or accepted stage after TTL deletion. Expired previous-stage detail does not manufacture accepted history: advancement remains HOLD for reconciliation.

Local default-off runtime engineering now includes actual signed private CRM source ingress/storage, immutable deployment funnel profiles, the current authorized Meta lead metadata resolver, opaque prepared events, durable stage settlement and trusted signed customer revocation/purge. `crm-runtime.ts` exposes the raw ingress router and verified-Meta-webhook recorder for host composition. `crm-source-store.ts` checks the global scope/lead tombstone in the same Firestore transaction as reingest; encrypted sources expire within seven days, while signed-delivery hashes and replay/revocation checkpoints retain ninety days. Fresh lead reads compare stable registry/provider facts while preserving the original observation clock; they never blindly renew it.

Deployment configuration is disabled by default. `LUMIN_CRM_SIGNALS_ENABLED`, `LUMIN_CRM_SOURCE_INGRESS_ENABLED`, `LUMIN_CRM_PROFILES_JSON`, `LUMIN_CRM_SUBJECT_HMAC_KEY` and per-profile `LUMIN_CRM_INGRESS_KEY_*` references require approved server-side configuration. Profiles bind exact tenant/client/app/Pixel, separate source and dispatch connections, Page, account, subscription, CRM name and immutable ordered stages. JSON contains secret references only. No configuration or credential is installed by these changes.

The local host now composes raw CRM ingress and verified Meta webhooks with the canonical guarded dispatcher. Native synthetic end-to-end tests exercise actual signatures, current authorized lead reads, encrypted sources, protected human approval, exact Graph body, acceptance, unknown outcomes and withdrawal/rotation denials. The remaining provider release gate is actual current CRM token compatibility inspection. Current primary CRM documentation instructs generating a dedicated CRM Pixel token but does not establish its debug-token type/app/scope semantics in the retrieved pages; ordinary USER/system-user compatibility is not invented. Production egress must remain HOLD until that exact credential proof exists. Synthetic source/journal tests are not live-provider certification.


Required composite indexes are `scopeHash ASC, leadHash ASC` on platform_crm_sources and platform_crm_stage_journal. Raw CRM sources retain at most seven days. Signed Meta origin references, delivery hashes, stage/audit metadata and customer-revocation safety tombstones retain ninety days, with TTL on expireTime. Customer purge removes encrypted signed Meta lead origin as well as source/stage/audit records; insertion checks relevant tombstones atomically so delayed Meta webhooks cannot restore purged customer data. Disabled dispatch still accepts correctly signed scope-bound customer withdrawal. Runtime configuration drift rejects operations until restart/review; returned profile/key copies cannot alter private trusted configuration.


The permanent platform_crm_no_resend collection has no TTL: stage_<stageHash> records hold only scopeHash/leadHash/stageHash/state, customer_<scopeLeadHash> records hold scopeHash/leadHash/CUSTOMER_REVOKED, and scope_<canonicalScopeHash> anchors the subject-HMAC key fingerprint and immutable funnel digest. Changing subject-HMAC key or funnel pack after restart cannot silently create a new namespace; it requires an explicit migration preserving prior history. Encryption key rotation is a separate concern. These HMAC-derived identifiers are pseudonymous safety metadata, not anonymous data or customer payloads. No-resend barriers survive customer purge and bounded source/detail TTL deletion.

## Concrete credential-waiting USER inspector

The default-off `LUMIN_CRM_USER_CREDENTIAL_INSPECTION_ENABLED=true` selects the concrete `MetaCrmUserCredentialInspector` at HTTP startup. It needs the existing secure `META_APP_ID`/`META_APP_SECRET` and an already enrolled selected USER credential with the conservative Lumin `ads_read`/`ads_management` pack. It pins the actual Graph version/app-secret configuration and rejects later changes. No raw key or token is stored in JSON or emitted in errors.

Before a CRM journal attempt and again before transport, the inspector performs fixed actual same-app `debug_token` inspection (valid USER, exact app/user/scopes/finite expiry), `/me` identity, complete `/me/permissions`, actual account identity/business and current literal `MANAGE` or `ADVERTISE` task observation, and complete bounded account `/adspixels` membership for the exact registered Pixel. Every read remains under the current selected execution permit; credential ciphertext, membership, human owner evidence and privacy revocation are rechecked. The resulting local observation expires within60seconds and binds the token fingerprint, app and Pixel. It does not certify CRM-specific token products or universal Meta permission minima. Primary identity contracts are the existing reviewed [Facebook manual-flow guide](https://developers.facebook.com/documentation/facebook-login/guides/advanced/manual-flow) and [access-token guide](https://developers.facebook.com/documentation/facebook-login/guides/access-tokens); account/Pixel fields and membership use the pinned official Marketing SDK contracts already used by guarded Marketing transport.

Dedicated Events Manager generated tokens and system-user inspection remain explicit HOLD in this inspector: their exact debug type/identity/access strategy is not guessed. A different credential type requires a separately verified concrete adapter. Actual CRM event transport still reports only an exact provider accepted count; it does not infer delivery or optimization from successful inspection. This USER implementation is locally exercised with synthetic inspected Graph fixtures and the real signed-source/human-approval/native-MCP path, not live-provider certification. The feature and ingress remain disabled until deployment configuration and credentials are deliberately supplied.
