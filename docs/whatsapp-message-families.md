# WhatsApp reviewed message families

The candidate implements separately human-approved text-only UTILITY template sends, interactive reply buttons/lists, and JPEG image sends. These are engineering fixtures and guarded transport implementations; they are not live Meta acceptance or production deployment evidence.

Every send selects the same registered client phone, Messaging Account and WhatsApp Account, verifies the actual BISU app/subject/granular grants and business, requires a fresh owner-reviewed phone assignment, then consumes one exact-plan human approval. Recipients and inbound message bodies are not written to terminal audit metadata. A provider response yields only one message receipt ID; network uncertainty remains UNKNOWN and is never automatically retried.

Interactive and JPEG sends require independently trusted client opt-in plus a signed inbound customer-service window. Approved UTILITY templates additionally require the actual current template content to match the complete human-reviewed text snapshot, including positional substitutions. Current authenticated template inspection supplies approval evidence; model input cannot set consent or evidence. The final synchronous deadline check follows all asynchronous revalidation immediately before the mutation claim.

JPEG sends use signed actual-byte media intake, decoding and an immutable approved-CDN assertion. Human media enrollment is separate from send approval. The MCP input contains a registered media ID and optional caption; the server privately decrypts the consumed enrollment proposal to obtain the exact bound URL. Sources are purpose-bound to WhatsApp messaging and one registered phone. The local candidate accepts JPEG only, caps it at 5 MiB, and retains the existing narrow dimension/aspect bounds. This does not claim Meta lacks other image formats or message types. No arbitrary URL fetch, media upload, tracking destination, OTP/PIN or billing change is performed.

Primary contracts: [Meta image message example](https://www.postman.com/meta/whatsapp-business-platform/request/u5m7uk7/send-image-message-by-url), [Meta template text example](https://www.postman.com/meta/whatsapp-business-platform/request/o65u5m5/send-message-template-text), [Meta reply-button example](https://www.postman.com/meta/whatsapp-business-platform/request/ne00kt6/send-reply-button), and [Meta media types and limits](https://www.postman.com/meta/whatsapp-business-platform/folder/13382743-ecb27be5-4d27-4763-bbee-6a8002c04bf3). Current external-client access review, live permissions, client consent, Meta app configuration and owner acceptance remain separate release gates.

Provider template status/content and rights are fresh preflight observations. Meta can change external state after observation and before dispatch; this implementation does not claim an atomic Meta template-version lock. An accepted message receipt proves submission, not delivery.

Stable eligibility observations require durable records issued by an authenticated human review workflow, with current issuer/scope/expiry and final revision checks. A source URL or embedded verified=true alone does not grant eligibility. Such human observations do not establish actual App Review, current provider acceptance or delivery; dedicated transports retain their actual credential/access/content/consent checks.

## Additional attachment sends

The candidate also has `whatsapp_platform_send_audio`, `whatsapp_platform_send_video` and `whatsapp_platform_send_document`. They reuse the existing dedicated WhatsApp transport's actual same-app BISU subject/granular-scope/client-business/dual-account/phone proof, current recipient opt-in, trusted inbound window, separate exact human send approval and single mutation claim. Model input selects only an enrolled `media_id`; the approved URL is decrypted privately and is never accepted as a model-provided media URL.

Source rights are separate from Messenger rights: `whatsapp_messaging_audio`, `whatsapp_messaging_video` and `whatsapp_messaging_document`. MP3/PDF signed ingress and human enrollment use `LUMIN_MESSAGING_ATTACHMENTS_ENABLED` (the earlier Messenger-only flag is a compatibility alias; conflicting values fail closed). MP4 uses the existing publishing-video source configuration with the exact WhatsApp phone root and send mode. Source authority is READ/WRITE_MESSAGING only, with no Page-task transfer, financial access or automatic rights extension.

Current official primary request examples describe [audio links](https://www.postman.com/meta/whatsapp-business-platform/request/juzqcg2/send-audio-message-by-url), [document links](https://www.postman.com/meta/whatsapp-business-platform/request/zdgzfmt/send-document-message-by-url) and [video links](https://www.postman.com/meta/whatsapp-business-platform/request/eumudql/send-video-message-by-url). The guarded requests use the corresponding typed media object. Optional captions are limited to video/document; voice mode, arbitrary filenames, uploaded media sharing, contact/location/commerce payloads and unknown fields remain excluded from these exact contracts. MP3 is actual fully decoded audio; PDF remains an explicitly opaque signature-and-digest check, with the human review limitation stated. Local byte, codec and duration limits are conservative application limits.

Native SDK fixture journeys exercise all three source enrollments and separately approved sends with synthetic credentials and fake provider responses. They do not prove live WhatsApp acceptance or delivery. Provider/API approval and authorized staging acceptance remain separate release gates.
