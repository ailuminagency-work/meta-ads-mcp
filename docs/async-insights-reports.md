# Approved bounded asynchronous Insights reports

`marketing_create_async_report` creates one account-level report job through a fixed authenticated `POST /v26.0/act_ID/insights`. The current official SDK's `get_insights_async` defines this POST and its `fields`, `level`, `time_range` and unified-attribution request parameters. Its async edge parser explicitly normalizes a returned `report_run_id` to `id`. There is no invented `async` flag.

Lumin accepts only explicit real calendar `since`/`until` dates spanning at most31 inclusive days and not ending after current UTC date. The dates describe the advertiser's account calendar, not a conversion of event timestamps. Fixed fields are account ID, date bounds, impressions, clicks, spend, reach, frequency, CTR/CPC/CPM and action/cost-per-action observations. Account-level and unified-attribution true are server-owned requested settings; the latter is not a certification of actual provider attribution or account settings. Breakdown/filter/export/email/raw options are excluded.

The local operation class is WRITE_CONTENT solely to require a separate exact human action approval and durable single attempt. Actual current client/account grants, conservative ads_read USER/system-user scope and independent Marketing access review are required. The existing platform ownership/financial gate also applies; the report requests no ad, spend, billing transfer or activation. Actual USER OAuth enrollment supports the exact report capability and original report READ capabilities without adding ads_management. System-user OAuth enrollment is not invented by this module.

The strict creation receipt must contain a bounded numeric `report_run_id`; a present error marker is rejected even on HTTP200. The account-bound POST is the creation provenance. Atomic completion registers REPORT under that exact account and derives an immutable requested definition from the approved plan. It does not certify job completion. A lost or malformed receipt remains UNKNOWN and cannot reuse approval or automatically retry. A current-state change after the provider returned a valid ID causes PARTIAL with no newly granted report authority, preserving reconciliation of the known receipt.

Original `ads_get_report_status` and `ads_get_report_results` read only registered reports and require actual returned report ID/account ID. Results additionally require exact `Job Completed` and100percent and expose one bounded page. Minted definitions constrain result fields to the requested pack and are identified separately from preexisting reports. Missing metrics are unknown, not fabricated zeros; job completion does not prove all pages or business outcomes.

Primary sources: [current AdAccount SDK](https://github.com/facebook/facebook-python-business-sdk/blob/efd8423a2e595ea8d4c04eb824ce113f2f1d68cd/facebook_business/adobjects/adaccount.py), [async parser and report receipt mapping](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/abstractcrudobject.py), [report node SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/adreportrun.py), [official async example](https://github.com/facebook/facebook-python-business-sdk/blob/main/examples/async.py). Generated SDK evidence establishes transport/schema, while the conservative Lumin permission/access policy is stated separately.

The original `ads_create_async_report` name now maps to the separately approved fixed account report above. Its strict schema requires explicit `since`/`until`; unsupported fields, exports and arbitrary options are rejected. The original `ads_run_report_and_wait` name is an observational replacement for an already registered report: it never creates a job or hides a mutation. It permits zero to30 seconds of local waiting, at least5 seconds between status polls, current authorization before and after every provider read, and no mutation retries. Completion means an actual `Job Completed`/100 status receipt; results require the separate bounded results tool. Default zero waiting still permits one bounded status request.
