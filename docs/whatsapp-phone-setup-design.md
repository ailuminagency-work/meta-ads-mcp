# WhatsApp setup-only onboarding design

Status: implemented as a default-off candidate, with real provider/service/browser-route and Firestore transaction-adapter fixture tests. Independent security review is in progress; not enabled, deployed or production accepted. No live phone, credential, verification code or PIN has been submitted.

The current normal WhatsApp OAuth adapter proves an actual CONNECTED phone before creating ordinary connections/grants. That is a useful boundary and must remain intact. It also means an unregistered phone cannot use an ordinary connection to perform its initial registration. A separate encrypted setup-only credential lease and human workflow now handles registration without weakening the normal adapter.

Primary sources checked on 2026-10-16:

- [Current registration guide](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/registering-phone-numbers), updated June28,2026, uses v26 examples and states Embedded Signup v2/v3 deprecation October15,2026. Embedded Signup normally handles phone creation/code delivery/verification; registration is a separate fourth step.
- Its actual linked [Register API reference](https://developers.facebook.com/documentation/business-messaging/whatsapp/reference/whatsapp-business-phone-number/register-api) renders version23 and documents the Cloud API's two-permission bundle `whatsapp_business_management` and `whatsapp_business_messaging`. A conservative setup profile can require both existing granted permissions; this is not a claim of endpoint-specific minimum scopes.
- The guide links Request Code to a **pre-verified phone number** reference, rather than the older similarly named ordinary phone reference. That identity detail must be resolved before enabling request-code execution; exact target IDs cannot be interchanged based on spelling.

Implemented candidate boundaries:

1. A deployment-owned immutable setup profile binds tenant/client/operator/app/configuration ID, client business, WhatsApp Account, Messaging Account and exact prebound phone, with fresh owner review and finite owner-approved expiry. It has no ordinary platform capabilities, grants, financial operations or credit-line changes.
2. Separate OAuth state/nonce/session/profile binding produces an encrypted setup-only BISU lease after actual same-app token inspection, client_business_id, exact granular scopes and registered phone/dual-account checks. The lease lasts at most15minutes and never outlives provider/data-access/owner expiry. Its secret is unavailable to ordinary execution clients or MCP.
3. The UI offers only documented, independently reviewed setup actions. Request-code uses fixed SMS/VOICE and language; verification uses a six-digit code; registration uses the client's six-digit PIN. A new PIN changes the client's credential and must be entered/submitted by the human. No code or PIN goes to MCP, registry, audit, job hashes or logs, and no PIN is generated for the client.
4. Each action uses current authenticated admin membership, actual provider proof, exact profile and phone scope, signed one-use CSRF review and a durable pre-egress claim. OTP/PIN stay only in request memory. No automatic retry. Unknown provider outcomes keep a permanent hashed phone/action lock until supervised reconciliation.
5. Setup states use actual documented verification facts, not invented connection-status enums. Registration is separate from proof that Meta now reports CONNECTED. Ordinary OAuth and its current CONNECTED proof are still required before messaging or account grants are installed.
6. New lease/command stores require real Firestore transactions, bounded retention, exact actor/provider-app-user privacy provenance and active encrypted-secret erasure. An unknown claim cannot disappear through TTL and allow replay. Current tenant/member/client/root records must be checked atomically at each claim; a separate store cannot rely on stale external repository reads.

Required independent review must cover OAuth/session substitution, wrong app/business/phone/root IDs, code/PIN leakage, pre-verified-versus-ordinary phone identity, privacy locks, concurrent claims, stale owner context, lost provider responses and absence of ordinary grants. Fake-provider/unit success alone does not enable live setup.

Runtime configuration: LUMIN_WHATSAPP_SETUP_ENABLED=true and a deployment-owned LUMIN_WHATSAPP_SETUP_PROFILES_JSON are required. The factory also requires the exact named Meta app/secret, encryption key, secure session secret, and HTTPS callback origin. Actual setup mutations additionally require the platform and agency write flags. Defaults remain off. The profile owner review must be no older than five minutes at consent, and its approved lifetime cannot exceed one hour. No ordinary connection or grants are installed by setup.

The actual token-family discriminator is the documented BISU-only /me?fields=client_business_id result, bound to the inspected subject and exact client business; no undocumented debug_token.type enum is invented. The current registration guide names the same created business phone ID for request_code, verify_code and register. Its linked pre-verified reference remains a documentation mismatch to resolve through independent review before live activation.

Uncertain outcomes retain the hash-only app/phone lock and CLAIMED/UNKNOWN command without TTL. The encrypted token lease expires after at most fifteen minutes. There is no automatic unlock or resend: human provider-state reconciliation is required. OTP/PIN values and their hashes are never persisted. The setup UI is a separate authenticated human channel; neither field is accepted by MCP.

Verified-state reconciliation is available through a separate signed human review at `/platform/whatsapp-setup/lease/<lease>/reconcile/<command>`. It performs only fixed read inspection using the current unexpired encrypted lease. A held VERIFY_CODE can settle only when Meta actually reports VERIFIED; a held REGISTER can settle only when Meta actually reports CONNECTED. The exact stored command and global phone guard are updated/released atomically. No code, PIN or registration request is resent. SMS/VOICE delivery cannot be proven through this state inspection and remains held. Expired lease/owner review requires manual reconciliation; this feature never extends either expiry.
