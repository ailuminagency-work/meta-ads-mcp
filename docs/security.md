## Mutation boundary

Nothing starts spend or delivery, raises a budget or sends a Meta write without the correct policy class, a one-use human approval that the MCP caller cannot grant to itself, and PAUSED-only creates. The boundary is enforced in `evaluatePolicy` (class, role, ownership and writes flag) and in `authorizeOperation`, which every mutating path reaches with `writesEnabled` taken from `platformWritesEnabled()`; read-only callers pass `false`, so a plan that classifies as anything but READ is denied. `classifyPlan` rejects padded, aliased and unpause activation spellings and any create or copy whose status is not PAUSED (`tests/platform/activation-routes.test.ts`, 353 cases through the plan builders and the real MCP server).

In a strict read-only agency deployment the tools without `readOnlyHint` make only GET requests to Meta and write only the records they are documented to create; `tests/platform/read-only-agency-surface.test.ts` runs each one end to end with a writes-enabled control so a denial cannot be a fixture accident. Read-only does not mean the store is untouched: evidence and enrollment proposals are stored, which is why those tools carry no `readOnlyHint`.

Three properties of that boundary are worth stating separately. A plan that finishes UNKNOWN or PARTIAL holds a per-plan lock that only SUCCEEDED or FAILED releases, so the identical request cannot be re-approved and sent twice. Separation of duties is on by default in an agency deployment that can write; only `LUMIN_APPROVAL_REQUIRE_DISTINCT_APPROVER=false` turns it off and an invalid value turns it on. And one write class has no human approval by recorded exemption: `signals_send_pixel_events` (WRITE_NON_FINANCIAL) sends a stored, consented first-party event once both write flags are on and needs an `approval_id` threaded through before an agency that wants the strict invariant enables platform writes. Details are in [policy-engine.md](policy-engine.md).
