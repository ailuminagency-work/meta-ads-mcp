# Operations and rollout gates

Flags default off: LUMIN_PLATFORM_ENABLED, LUMIN_PLATFORM_WRITES_ENABLED, LUMIN_PLATFORM_WEBHOOKS_ENABLED, LUMIN_PLATFORM_OAUTH_ENABLED, LUMIN_PLATFORM_MESSAGING_POLICY_ENABLED and LUMIN_PLATFORM_SIGNALS_ENABLED. Mutations additionally require AGENCY_WRITES_ENABLED=true. Invalid platform/webhook flag values fail closed. Webhook mounting requires both platform and webhook flags plus a trusted environment subscription/index configuration or reviewed injected dependencies.

Do not enable the feature in production until strict legacy migration, OAuth adapters, human approval issuance, fresh-grant refresh, registry bootstrap and host event runtime are reviewed and accepted. Disabling the platform flag restores the legacy route; disabling the write flags prevents platform mutations. No flag changes are authorized by this branch.

Webhook operations require Firestore queue indexes, expireTime TTL, a supervised retry scheduler, DLQ access, metadata-only monitoring and idempotent adapters. Claims reject expired events immediately even while asynchronous TTL deletion is pending. Retention defaults seven days and is bounded at thirty; optional encrypted payload storage is not enabled.

On ambiguous provider write, reconcile operation state using observed provider state before considering a new approval. Revoke affected connections/grants on ownership reassignment. Refresh freshness evidence under least privilege; never relax the freshness clock to keep a stale token working. Monitor counts/status/request IDs only; never customer messages, tokens or raw callback URLs.

**Before enabling platform writes after the release that added operation plan locks.** Plan locks start at deploy: an operation that was already UNKNOWN, PARTIAL, PREPARED or EXECUTING before then has no lock row, so its identical plan can still be requested, approved and sent again. List those operations for every tenant (the `operations` records in those states; a PREPARED or EXECUTING one older than the five-minute authorization window is a crashed attempt), compare each with the observed provider state, and record the outcome by hand before the write flags go on. After the release, an operation that ends UNKNOWN or PARTIAL holds its plan: the identical request is refused `PRIOR_ATTEMPT_UNRECONCILED` at request, review, issue and execution, the approval stays unspent, and a deliberate retry after reconciling means a changed plan. There is no operator-driven release yet. Lock rows (`operationPlanLocks`) are never deleted: one small document per distinct mutating plan per tenant. Do not add a TTL to the collection until the retention decision is made, because an expired lock reopens a plan whose write may have happened.

First-party signal dispatch deduplication metadata has a fixed maximum retention of 90 days from the initial claim. Configure Firestore TTL on `expireTime` for the `platform_signal_dispatch` and `platform_signal_dispatch_audit` collection groups. State transitions preserve the original deadline and never extend it. TTL removal is asynchronous: a checkpoint still present after its deadline returns an explicit reconciliation HOLD on lookup, claim, or transition. The service never deletes or reclaims a stale checkpoint to enable a retry. After TTL removal, the original event is also outside the seven-day source-event freshness and encrypted-source retention policies; a trusted integration must never reuse an event identity for a new outcome. No automatic provider retry is permitted for UNKNOWN or ATTEMPTED outcomes.

First-party source revocations persist a hashed exact-scope tombstone even when ingestion has not arrived. Configure `expireTime` TTL for `platform_first_party_source_revocations` at 90 days. Delayed or concurrent ingestion cannot restore consent under the same source/consent references. The resolver checks revocations before returning decrypted source data. No missing-payload revocation fabricates an event or consent record.

Supervised lifecycle and operational host engineering

`createFirestoreOperationalHost` creates the real Firestore control store and authenticated HTTP router for deployment wiring. It derives user and worker identities through injected verified session/worker resolvers; request headers and payloads cannot select an operator. Lifecycle prepare records an exact connection snapshot, human approval uses signed same-origin CSRF protection, and execute has one durable provider mutation claim. Connection, encrypted credential, grants, command outcome and metadata audit complete atomically. Unknown refresh/revocation outcomes quarantine local access and never retry automatically. Grant verification time, capabilities and expiry are not extended by token refresh.

Facebook supports inspected short-lived user-token extension and supervised `DELETE /{user-id}/permissions` followed by invalidation inspection. Existing long-lived Facebook tokens require owner reauthentication; the service does not invent a refresh endpoint. Provider-wide revocation is blocked when another active connection shares the same app/user scope. Threads supports the documented long-lived token refresh after24hours, exact same-app debug inspection and local revocation. A current programmatic Threads-wide revocation endpoint was not established by official documentation; that action requires the owner's provider UI, while read-only invalidation inspection is available. These are provider contract limits, not synthetic completion.

Worker jobs begin PAUSED, have deterministic scoped cursors, bounded leases and attempts, explicit revision-bound pause/resume/DLQ replay, and only accept reviewed read-only or durable-idempotent adapters. The authenticated worker tick reads at most20 jobs across at most10 exact scopes. A stale lease cannot overwrite a newer worker's outcome. A worker delivery adapter must prove its external idempotency contract before activation. Jobs expire within7days; lifecycle commands, reconciliation metadata and operational audits expire within90days. Configure `expireTime` TTL for `platform_lifecycle_commands`, `platform_worker_jobs`, `platform_reconciliations` and `platform_operational_audit`.

Production bootstrap is a pure dry run. It validates exact project/service-account/origin/release identity, requires all write/worker/signal/messaging flags disabled, and returns reviewable IAM, index, TTL and acceptance plans. It never applies cloud configuration. Owner approval, independent review, live-provider acceptance and deploy authorization remain separate gates.

Registry bootstrap also validates a complete proposed tenant/member/client/asset-parent/operator-index closure. `dryRunRegistryBootstrap` rejects credentials, grants and approvals; detects foreign or ambiguous parent relationships, cycles, stale source provenance and mismatched client ownership; and emits deterministic Firestore paths with an expected-absent or exact-before-hash prerequisite for each proposed record. This remains an owner-review artifact with no apply function.

The staging dry-run also covers paused-ad batch metadata (90days), human eligibility observations (at most1day), hashtag quota records (7days), private research jobs (7days), research approvals (at most1day), and settled research financial checkpoints (90days). Research budgets receive TTL metadata only when reserved spend is zero. Unresolved checkpoints and reserved budgets have no expireTime: deletion must never release spend uncertainty. WhatsApp setup phone locks likewise have no TTL. Business-owner artifacts currently have no storage TTL; their authorization expires within24hours and subject erasure removes their records. An infrastructure TTL policy alone does not impose these conditions; the serializer controls whether expireTime exists. Review both before staging installation.

`REFRESH_GRANTS` is a separate supervised action from token refresh. Its provider inspector reads current account tasks and exact registered child-to-account relationships, or the matching Threads/business read-only root. It renews only existing capability/action/task subsets, and does not discover or grant additional assets. Ownership/billing proof has its own `ownershipEvidenceVerifiedAt` freshness boundary; access refresh preserves that timestamp and cannot renew old ownership attestations.

The supervised grant-refresh worker can also renew preexisting webhook-index leases through `createFirestoreWebhookIndexRefresher`. Deployment configuration must supply each exact app/product/asset/client mapping. A transaction checks a recently completed successful grant inspection, current active client/operator/connection, matching asset and READ grants, and the unchanged existing mapping before renewing only its verification and expiry timestamps. Missing, revoked, foreign or unconfigured mappings are never created or discovered. Renewal is bounded by actual grant/token expiry and the one-hour inspection window. Storage failure keeps webhook delivery on HOLD; it does not report successful renewal or renew ownership evidence.

Provider-wide Facebook revocation claims a global app/user lifecycle lock before the single DELETE attempt. The lock hash excludes tenant identity so another tenant cannot enroll a new connection during revocation. Configure90-day `expireTime` TTL for `platform_lifecycle_locks`; an expired lock still present remains a HOLD. Both known-success and uncertain outcomes retain the lock. OAuth enrollment must transactionally reject any present lock. There is deliberately no automatic unlock or model-controlled lock deletion. Early unlocking needs separately supervised provider reconciliation and fresh owner consent; this candidate does not fabricate that proof or expose an unsafe unlock endpoint.

The HTTP runtime remains disabled unless `LUMIN_PLATFORM_OPERATIONS_ENABLED=true` and the main platform is enabled. `LUMIN_OPERATIONAL_WORKERS_JSON` contains deployment-owned worker IDs, unique `LUMIN_WORKER_KEY_*` secret references, exact tenant/client/asset scopes and allowed adapter IDs. Keys are 32 random bytes encoded as hexadecimal and belong only in the platform secret store. Internal tick requests sign the worker ID, millisecond timestamp, random 64-character hexadecimal nonce, POST method and exact `/platform/operations/internal/worker/tick` path. The service atomically consumes each nonce, accepts at most sixty seconds of clock skew, and ignores caller-provided operator identities. Configure `expireTime` TTL for `platform_worker_leases`; nonce records have a two-minute retention bound and any record still present remains replay-blocking.

Page, Messenger and linked Instagram task grants currently renew through fresh supervised OAuth. The enrolled Page token alone does not replace the fresh USER `/accounts` task proof used during enrollment. Independent Instagram Login also renews permission evidence through a fresh code exchange: the [official Business Login contract](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login) returns granted permissions during code exchange, while long-token refresh returns only the token and expiry. Identity inspection or stored historical scopes are not treated as current task/permission evidence, and undocumented permission/debug endpoints are not called. These providers remain unavailable for unattended grant renewal until an independently verified inspection contract is implemented.

Optional `LUMIN_OPERATIONAL_INGRESS_JSON` maps exact tenant/client/asset/product scopes to a current administrator's operator ID. Only already signature-verified webhook batches reach this hook. They create paused deterministic jobs for `local_inbox_leads`, `local_inbox_pages`, `local_inbox_instagram`, `local_inbox_messenger` or `local_inbox_whatsapp`; they never automatically resume jobs. Each must also match a configured worker scope and adapter. Delivery stores bounded metadata in `platform_event_inbox` with at most seven days of TTL; this is a local receipt, not delivery to an external CRM. A scoped existing inbox receipt supports recovery when provider-independent inbox delivery committed before the worker's completion record. Optional `LUMIN_WEBHOOK_INDEX_REFRESH_BINDINGS_JSON` supplies exact existing mappings for the supervised grant-refresh adapter. No configuration creates new authorization or invents provider proof.

OAuth session-store retention: the stores write an `expireTime` field on every record they create, and the reviewed TTL plan (`REQUIRED_TTL_PLANS` in the production bootstrap dry run) lists one policy per collection group: `mcp_auth_codes` (logical expiry plus one hour), `mcp_refresh_jti` and `mcp_session_jti` (logical expiry plus one day) and `mcp_clients` (90 days since last use; the server extends a client's deadline on use once fewer than 45 days remain, and only for a client the registration policy still accepts). `mcp_refresh_jti` also holds the code-redemption markers, family-revocation markers and rotation tombstones used for replay detection; each carries the same `expireTime` rule, so none outlives its logical expiry by more than a day and none is reaped before it. Creating the Firestore TTL policies themselves is a separately approved operator action: this repository only emits the plan and writes the field, it never applies a policy. Until a policy exists, or while Firestore's asynchronous deletion lags, dead records are only retained longer, because application expiry is still enforced on read. Clients stored before this change have no `expireTime` and are never reaped until their first use after deployment backfills it. A registered client must outlive its 30 day refresh chain; do not shorten the client policy. These stores hold no privacy tombstone or financial checkpoint. Records that do (`platform_meta_privacy_subject_locks`, `platform_meta_privacy_provenance`, `platform_crm_no_resend`, `platform_whatsapp_setup_phone_locks`, business-owner attestations, and unresolved research checkpoints or reserved budgets) must never receive a TTL policy.
