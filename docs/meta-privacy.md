# Meta deauthorization and user-data deletion

This candidate implements authenticated Meta callbacks, immediate actual app-user locks, resumable credential revocation and active scoped erasure. It remains default off until configuration and independent acceptance are complete. No production configuration, index or TTL is applied by these modules.

`LUMIN_META_PRIVACY_ENABLED=true` requires strict deployment-owned `LUMIN_META_PRIVACY_IDENTITIES_JSON` entries `{id,appId,secretReference}` and `LUMIN_META_PRIVACY_WORKERS_JSON` entries `{id,secretReference,allowedAppIds}`. Identity references contain existing app secrets in the platform environment. Worker references must use distinct `LUMIN_PRIVACY_WORKER_KEY_*` values of64hex characters and must not reuse app secret references. Callback URLs are `/meta/privacy/<id>/deauthorize` and `/meta/privacy/<id>/delete`; Meta submits form-urlencoded signed_request. The callback checks exact HMAC-SHA256 base64url signature and bounded issued-at freshness. This local24-hour freshness policy is narrower than signature verification alone.

Callback identity is the actual provider app-user, stored as immutable connection.metaAppUserId, never the platform Facebook operator or Page/professional-account ID. Page identity comes from the inspected same-exchange USER credential. Independent Instagram identity comes from the actual short-token user ID, which can differ from the professional asset ID. Legacy records require exact provider-specific proof; ambiguous old Instagram/Page identity HOLDs instead of guessing.

The first transaction persists `platform_meta_privacy_subject_locks` and a deduplicated job/hashed receipt before scanning any tenant. Matching connections across all tenants are discovered using bounded collection-group pagination. Exact connection paths, credential/delegation identity, app/user binding and grant paths are checked. Matching credentials and purpose-bound USER delegations are actively deleted; connections are revoked and grants removed in100-row steps. Existing operator locks are added as a compatibility boundary. New authorization, enrollment, supervised refresh and event consumption must honor actual-subject locks.

An app-scoped internal worker sends signed POST `/meta/privacy/internal/worker/tick` with `{job_id}` and x-lumin-worker/timestamp/nonce/signature. Signature includes exact method/path/body digest. Nonces are durably single-use. Each call executes one bounded stage. This is a private server worker boundary, not an MCP tool or public bearer bypass. External scheduling remains separately configured; the application does not invent a running scheduler.

The provenance index binds new encrypted plans and personal metadata to exact authenticated app-user identities in the same transaction as the target. Erasure actively deletes indexed targets; the minimal hashed index has no independent TTL while its target survives. Legacy cleanup walks bounded allowlisted collections with durable cursors and exact path validation. Exact connection-owned plans and platform-actor metadata for the configured authentication app are deletion targets. Shared client assets and unrelated client customer sources are retained. Specific ambiguous legacy records lead to HOLD; complete means the defined OAuth-user scope was actively processed, not that unrelated client-owned customer data was deleted.

Receipt status contains no raw app-user, client identity, credentials or payload. DELETE completion is distinguished from deauthorization completion. TTL is asynchronous retention cleanup, never immediate erasure proof. Locks are retained pending separately reviewed fresh-consent reconciliation; callback code never silently removes existing or expired-present locks.

Infrastructure dry-run requirements: collection-group connections query on appId plus document name; ordered scans for allowlisted legacy collections; provenance subjectHash plus document name; grant connectionId plus document name. Review actual Firestore index requirements before enabling. Unfinished privacy jobs, receipts, connection targets, hashed subject locks and provenance have no independent TTL; losing them could discard unfinished deletion work or resurrect access. Completion actively deletes temporary target records, scrubs job app/user identifiers and starts90-day job/receipt metadata TTL. Subject locks remain hash-only and permanent until explicit separately reviewed re-enrollment; no automatic unlock occurs after90days. Worker nonces are2minutes. No migration or live TTL enablement is performed here.

All tests use fake providers and fake Firestore. Live Meta callback registration, account consent, privacy policy/business requirements and production runtime acceptance are separate gates.

Configured Facebook authentication-app callbacks additionally invalidate legacy authcodes and refresh/session JTI allowlists and actively delete exact users/<appUserId>/meta_tokens. A DELETE also deletes the exact user's Apify/Gemini secret subcollections, profile, canonical operator index and matching tenant membership rows using bounded pagination; unrelated users, tenants, clients and shared assets remain. Session/access/refresh verification and new issuance honor the persistent authentication-user lock. Personal credential/profile/authcode/JTI writes read that lock in the same Firestore transaction as the write, preventing an in-flight login or refresh from reintroducing data after erasure.

Platform authentication actors and independent provider app-users are different identity domains. Legacy actor metadata is associated through the exact job/tenant/operator mapping produced from a verified matched connection. A numeric collision with an unrelated provider user never proves ownership. Explicit same-app actor metadata can be erased using that mapping; legacy actor-only records without app/connection proof report a specific HOLD. For the configured Facebook authentication-app callback, the authenticated Facebook principal itself is the exact platform actor across products and tenants; that withdrawal also revokes its other product connections and locks each actual provider subject.

Root operational lifecycle commands containing exact actor/approver/connection identifiers are included in bounded cleanup. Worker jobs that contain only client-owned asset scope and an opaque command hash, reconciliation digest records and operational audit with hashed scope are retained as minimal security/client metadata. The Instagram hashtag quota ledger is shared tenant/client/app/professional-account state containing hashed public queries and public IDs, with7-day reservation retention. It is KEEP_SHARED_CLIENT_QUOTA, not personal-user query data; deleting it on one operator's withdrawal would lose PENDING/UNKNOWN reservations for other authorized client operators. Full client disconnection/purge is a separate operation.

Paid-research financial checkpoints and client monthly budgets are KEEP_SHARED_CLIENT_FINANCIAL. They contain no operator identity, query or research results. The checkpoint retains only exact client/app/provider billing scope, hashes, bounded cost state and an encrypted opaque provider job reference needed for free reconciliation. An individual operator withdrawal deletes personal research jobs/approvals through the owned-record provenance path, but cannot erase an unresolved cost reservation or permit a second paid attempt. Unresolved checkpoints and budgets with reserved funds have no automatic TTL; confirmed settled checkpoints receive a 90-day metadata TTL. This retention is cost safety, not proof that a vendor erased its own data or canceled a job. Full client purge and vendor obligations require separate review.
