# Messenger attachment candidate

The candidate implements separately reviewed video, MP3 audio and opaque PDF attachment sends for an enrolled client-owned Messenger Page. It remains disabled by default and has no live-provider acceptance evidence.

The provider request is the fixed Messenger Send API `/PAGE/messages` endpoint, with the selected Page credential, exact numeric recipient, `messaging_type: RESPONSE` and `message.attachment` containing a server-verified source URL. The reviewed primary reference is [Meta Messenger Platform API](https://www.postman.com/meta/messenger-platform-api/documentation/iyp204x/messenger-platform-api). Source metadata never creates Page access, MESSAGE task, pages_messaging permission, an App Review approval, or a recipient response window.

The video path reuses signed MP4 ingress and actual full decoding. A Messenger video has a distinct `facebook_messaging_video` purpose, a PAGE parent and only READ/WRITE_MESSAGING source authority. Publishing sources cannot substitute for messaging sources. Video uses the existing conservative local 16MiB, 3–60 second H264/AAC envelope.

Audio and PDF use separate `attachmentEvidence` and encrypted `attachmentProposals` records. Audio is MP3 only, actually inspected and fully decoded through fixed pipe-only ffprobe/ffmpeg processes; allowed sample rates are 22050/24000/32000/44100/48000 Hz and one or two channels. Each subprocess has a 10-second deadline, 32MiB individual allocation ceiling and bounded output; only one audio decode runs at a time. The local source envelope is 8MiB and 0.1–60 seconds. These limits are conservative application choices, not asserted Meta format maxima.

A PDF is explicitly opaque: the adapter supplies exact bounded bytes, a PDF signature and final EOF marker are checked, and the digest is bound to the immutable approved URL and rights. The platform does not parse its contents, certify them safe, or claim that a signature makes a file harmless. The human review states that limitation and links the exact trusted source. An organization deploying this path must approve its source adapter and file handling policy.

Audio/PDF routes require `LUMIN_MESSENGER_ATTACHMENTS_ENABLED=true`, `LUMIN_PLATFORM_ENABLED=true`, an encryption key, session CSRF secret, numeric matching META_APP_ID and strict `LUMIN_ATTACHMENT_PROFILES_JSON`. Each profile binds a tenant/client/operator/connection/Page/app, exactly one audio or file purpose, an approved public hostname and a distinct `LUMIN_ATTACHMENT_INGRESS_KEY_*` reference. Ingress signatures cover raw bytes, the entire immutable profile, timestamp and delivery identifier. Models cannot set rights or attach arbitrary URLs. No URL is fetched by ingestion or sending; the separately trusted adapter must provide immutable bytes and hosting.

Source enrollment requires an authenticated browser review with exact-plan, principal, origin, secure-cookie and CSRF binding. It atomically creates the registered source, narrow grant and connection reference. Source proposals expire within five minutes and have a bounded Firestore TTL plan. They are included in OAuth-user provenance and erasure coverage. Lifecycle inspection preserves approved sources without renewing their rights, expiry or grant authority.

Every send requires a separate exact human approval and a current trusted signed inbound response window. The dedicated client rechecks current authorization and source-proposal identity after the asynchronous window lookup, then checks the finite window deadline immediately before its single mutation claim and provider POST. Unknown outcomes are never retried automatically. Provider receipts report acceptance only; delivery is not certified. Local approval and Meta processing are not a cross-system atomic transaction.

Remaining release gates include independent review, the frozen candidate's full checks, approved staging configuration, Meta permissions and a separately authorized live-provider acceptance. This document does not declare the overall V1 platform production-ready.
