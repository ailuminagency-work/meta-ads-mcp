# Instagram public hashtag lookup and quota

This module uses the Facebook Login User-token strategy only. The querying account is an exact registered, authorized client Instagram professional account. Instagram Public Content Access, provider-approved connected Page authority, external-client access and the exact scope pack remain independent runtime eligibility gates; documenting this API does not establish Lumin's approval.

Current primary sources are [Hashtag Search](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-hashtag-search), [Recently Searched Hashtags, updated August 17, 2026](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/recently_searched_hashtags), and [IG Hashtag, updated August 12, 2026](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-hashtag). The recent edge explicitly allows `limit=30`, avoiding its default page size of 25. Standard Graph field selection requests the documented hashtag `id,name` fields; names are used only transiently to identify an already-counted query.

Each call first reads current provider usage. A bounded, complete response can contain at most 30 distinct hashtag IDs and no continuation URL. The server supplies `user_id` from the authorized account and accepts only a lowercase ASCII tag subset of 1–100 letters, digits or underscores as local policy. Caller tokens, URLs, target accounts, fields and field expansion are rejected.

Before a new search, the server atomically reserves capacity in tenant-scoped `hashtagQuotas`. The key binds tenant, client, app and account. Records contain a SHA-256 query hash, public static hashtag ID when verified, timestamps, revision and PENDING/KNOWN/UNKNOWN state. No original tag, token or provider body is stored. Capacity counts the union of actual provider IDs and local reservations; an exact transient provider name match prevents double counting. Concurrent requests for the last available slot cannot both dispatch.

Successful static IDs can be returned from the verified local record, or an exact current provider-name match, without issuing a new search. An uncertain attempt remains capacity-consuming for its original seven-day window and cannot automatically retry. A later provider usage observation can reveal an exact ID without retrying the original search. Local reservations cannot lock third-party apps or coordinate their requests. Meta remains the ultimate cross-app quota enforcement authority. External actors and other apps can consume provider quota concurrently; the API remains authoritative and can reject a request after local reservation. Such failures retain conservative reservation state.

Quota state and its control audit commit transactionally against the exact current tenant, member, client, connection, assets and grants. A private in-process proof binds each allowed state update; there is no MCP quota setter or raw consent setter. Authorization and eligibility are rechecked before egress and before output. Public lookup IDs never enroll assets or create grants.

Configure Firestore `expireTime` TTL on the tenant `hashtagQuotas` collection. Runtime checks expiry synchronously; delayed TTL deletion cannot allocate extra capacity. Record retention is bounded to seven days after its newest reservation. App-user data deletion must remove quota metadata through the verified account/connection mapping rather than rely on TTL as immediate erasure. Deauthorization immediately blocks new provider requests through the shared execution-permit checks.

Tests cover native MCP dispatch, exact bearer-only requests, concurrent final-slot allocation, full/incomplete/invalid provider usage, uncertain transport without retry, revocation during usage reads, generic-client bypass, forged control writes, and the Firestore transaction/TTL adapter. These tests use fake providers and a fake database; they do not establish live feature approval or owner acceptance.
