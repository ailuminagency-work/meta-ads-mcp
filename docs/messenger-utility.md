# Messenger Utility integration

Utility templates use the separate `page_utility_messaging` permission and Page access token. Ordinary `pages_messaging` does not confer it. Current primary references: [Utility guide](https://developers.facebook.com/documentation/business-messaging/messenger-platform/send-messages/utility-messages), updated March13,2026, and [Page template edge](https://developers.facebook.com/docs/graph-api/reference/page/message_templates), v26.0. Page OAuth profiles derive the exact selected canonical scopes; no undocumented task alias or permission dependency is inferred.

The implementation supports owned-template metadata reads, separately human-approved text-only positionalBODY template creation, and separately approved transactional sends. Creation can legitimately return PENDING. Registration records the actual template ID under its Page; it does not authorize sending or certify approval. Immediately before sending, the dedicated client reads the actual Page-owned template by name and verifies exact registered ID, APPROVED status, UTILITY category, language and full reviewedBODY text. Unsupported header/buttons/media formats are rejected by this initial text workflow. Every send binds actual parameters to the approved plan and trusted transaction/consent payload digest. A provider receipt binds the recipient but does not establish delivery.

Signed Meta `message_template_status_update` notifications route to the Messenger Page asset index and the existing durable event queue after HMAC verification. They notify status change; their arbitrary payload fields are not accepted as approval authority. Every send still reads actual current provider status. Configure the Page subscription field and exact app/client/Page asset index through the existing human-reviewed bootstrap; webhook delivery remains an external validation gate.

`LUMIN_MESSENGER_UTILITY_ENABLED=true` enables the deployment-owned `/platform/messenger-utility/source/:adapterId` raw ingress. It also requires a32-byte hex `LUMIN_UTILITY_RECIPIENT_HMAC_KEY`, a secret at least32bytes in `LUMIN_UTILITY_SOURCE_SECRET`, and strict `LUMIN_UTILITY_SOURCE_PROFILES_JSON` scoped to the configured META_APP_ID. JSON contains only the whitelisted secret reference, never a secret. A trusted transaction backend signs exact JSON bytes with HMAC-SHA256 in `x-lumin-utility-signature: sha256=<hex>`. No MCP tool writes consent.

The source record binds tenant/client/app/Page, HMACrecipient, transaction and consent references, exact template ID, canonical template/parameter digest, nonmarketingpurpose, occurred time and expiry. Source events must be recent, finite and not future-dated. Withdrawal dominates equal-time grants. Replayed event IDs cannot reset authority. Only hashes, scoped metadata and decisions persist; original recipient IDs, template content and parameter values do not. Durable collections `platform_messenger_utility_transactions`, `platform_messenger_utility_events` and `platform_messenger_utility_audit` require Firestore TTL on `expireTime` (7days). Missing/expired evidence denies sending. Rotation of the recipient key makes prior bindings unusable.

This source is a trusted client integration boundary. A signature proves the configured integration submitted the record; it does not prove that a real customer consented. The client must connect its actual consent/transaction system and validate that flow before activation. Code and synthetic journeys do not establish Meta App Review, permission grant, webhook delivery, real customer consent or production acceptance.

The utility transaction records are classified `KEEP_SHARED_CLIENT_CUSTOMER_SOURCE` for an individual agency OAuth-operator deauthorization. They represent shared client-customer consent and are not inferred to be personal data of the agency operator. No operator/credential numeric identity is invented to delete them. Their explicit7day TTL remains mandatory; a separately authorized whole-client purge must address these collections. If a future ingress records actual submitting-operator personal provenance, that linkage must be explicit and separately covered by privacy deletion.
