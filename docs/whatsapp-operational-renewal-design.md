# WhatsApp supervised operational renewal design

The immutable owner-reviewed assignment is a consent boundary, not a provider access observation. Keep its original checkedAt, expiresAt, approvedBy and exact tenant/client/app/WhatsApp Account/Messaging Account/phone unchanged. Enrollment still requires the original owner review to be no older than five minutes. Operational renewal never extends this owner-approved duration or changes billing, scope, root assignment or client ownership.

A separate operational inspection should bind the canonical owner-evidence hash, stable connection and credential identity, actual BISU subject, app ID, client business, exact dual account and phone. A verified read adapter obtains actual debug_token scope/granular grants and /me client_business_id, then inspects the selected Messaging Account phone edge. Existing Flow/template child grants require their actual selected-parent edges; foreign children are discarded and never enrolled. All inspected asset IDs, parents and preexisting grant capability/action/task sets must match the durable approved snapshot.

Only a separately human-approved REFRESH_GRANTS command may atomically persist the new inspection and renew existing access freshness. The final transaction rechecks current principal/membership, original owner-evidence hash, app-user/privacy locks, credentials and all registered parent records. The new inspection deadline is bounded by five minutes, actual credential expiry, existing connection expiry and original owner-approved expiry. No manual timestamp or owner assignment is rewritten. Rights sources remain preserve-only and byte-for-byte unchanged.

Dedicated WhatsApp transports continue actual credential/access inspection before each egress. Older manual checkedAt can be accepted only while the original attestation remains unexpired and a current bound operational proof exists. An expired owner-approved duration still requires a new explicit owner review; token refresh or a provider GET cannot replace it. Deployment flags remain off until independent review and native operational regression acceptance.

The candidate now implements separate WhatsApp lifecycle and existing-grant inspectors, a stable owner/credential binding hash, a server-issued operational inspection record, and atomic supervised REFRESH_GRANTS persistence in the production host factory. Eight focused synthetic-provider regressions cover a ten-minute-old still-valid owner record, actual access failure, expiry, credential/owner rebinding, required human approval and owner changes during provider inspection. Existing WhatsApp transports require the fresh operational record after the initial five-minute review window and still inspect actual credentials before egress. This is not enabled production evidence. Shared durable human eligibility issuance remains a separate integration gate; no manual timestamps or consent duration are extended.

Stable external-app eligibility, owner assignment and applicable dashboard observations now use separate durable human-issued eligibility records. A real authenticated administrator reviews the exact connection identity and an opaque document-reference hash; runtime verifies that record, current issuer authority, scope, expiry and revision under the same authorization snapshot. These records are human observations, not actual Meta App Review or live delivery proof. Unknown requirement strings retain strict freshness. Current BISU, business, phone/child access, content state, customer consent and messaging window checks remain provider or trusted-source checks at dispatch. No model-facing evidence setter exists.
