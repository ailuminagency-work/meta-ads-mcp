# WhatsApp client onboarding candidate

The verified credential path is client-scoped Business Integration System User (BISU) authorization through Facebook Login for Business with an approved Embedded Signup configuration. Lumin remains the agency; the client's business portfolio, WhatsApp account, Messaging account, phone and billing remain client-owned. Generic direct-developer system-user token upload is not exposed through MCP or this adapter.

The [official access-token guide](https://developers.facebook.com/documentation/business-messaging/whatsapp/access-tokens), updated September 19, 2026, requires access to both the WhatsApp account and Messaging account. It states that the WhatsApp account does not yet have Graph endpoints and warns against depending on interim assignment cascade. Therefore, a separate fresh owner-reviewed assignment record is mandatory. This human evidence is explicitly labeled `META_BUSINESS_SUITE_OWNER_REVIEW`; it is not represented as an API-verified WhatsApp-account edge.

`createWhatsAppOAuthAdapter` accepts immutable deployment-owned bindings to the exact profile, tenant, client, app, verified client business, WhatsApp account, Messaging account and phone. The owner-review timestamp must be within five minutes at enrollment, and its authorization lease cannot exceed one hour. The authenticated tenant/client and registered client's verified business IDs must match before consent and again at callback. Caller-provided binding records or a URL alone cannot establish this authority.

The adapter performs only the documented authorization-code exchange and bounded read-only proofs:

- Same-app token inspection and exact effective scope comparison.
- The [documented BISU `/me?fields=client_business_id` field](https://developers.facebook.com/documentation/facebook-login/facebook-login-for-business) to bind the actual client business and inspected subject. A generic user/system-user token label is insufficient.
- The registered Messaging account's [phone-number edge](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/phone-numbers) to establish exact phone membership, requesting ID metadata only.
- The registered phone's documented `status` field, requiring `CONNECTED`.

The resulting credential lease is bounded by the fresh owner assignment lease and any finite provider token/data-access expiry. Zero provider expiry does not become unlimited service authority. Unknown fields, foreign IDs/scopes/businesses, absent assignment review, stale records, disconnected phones and unverified capabilities hold enrollment. No phone registration, verification-code request, app subscription, template creation, message sending or credit-line sharing occurs during onboarding.

Read profiles request `whatsapp_business_management`. Messaging profiles add `whatsapp_business_messaging` and its verified dependency; only separately verified product capabilities/actions are allowed. App Review, Tech Provider/Embedded Signup eligibility, client owner consent, independent dual-account assignment review, current recipient opt-in and service-window evidence remain distinct gates. Synthetic adapter tests do not establish live approval or successful owner onboarding.

Integration requires the protected OAuth core to accept the exact registered WhatsApp-account/Messaging-account/phone parent closure, call the adapter's enrollment-context validator, preserve client-business and owner-assignment provenance, encrypt credentials, and atomically write scoped connection/grants. The candidate is not a token-upload workaround, and no production configuration has been applied.

The client connection screen now launches the current documented Embedded Signup v4 SDK interaction (`FB.login` with config_id, code response, override_default_response_type and extras.setup). It keeps the existing server-generated state and HttpOnly browser nonce binding and sends only the exchangeable code to the existing protected callback. Facebook-origin session messages are advisory; their WABA/phone/business IDs never mint registry assets, grants or assignment evidence. One browser attempt cannot settle twice or accept a later callback from an older attempt.

This SDK launch does not prove that a Meta dashboard configuration was upgraded or that a new phone is registered. The verified server path still requires the prebound owner-reviewed client business/account/phone triple and actual CONNECTED phone proof. New client assets need independent owner review and registry enrollment; phone verification/registration/PIN are human Meta setup steps. No PIN, OTP or app secret enters MCP or the launcher. The deprecation warning on the current official implementation document says Embedded Signup v2 was deprecated October15,2026; this implementation does not use v2/v3 sessionInfoVersion extras. See https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/implementation and the current configuration/upgrade guidance before live activation. Fake SDK/browser tests establish engineering behavior only.
