# Policy and approvals

Classes: READ, WRITE_NON_FINANCIAL, WRITE_CONTENT, WRITE_MESSAGING, WRITE_AD_CONFIGURATION, WRITE_BUDGET, ACTIVATE_SPEND, DELETE, BUSINESS_ADMIN, IDENTITY_OR_ACCESS and BILLING. Decisions are ALLOW, DENY and REQUIRE_CONFIRMATION.

Global mutation flags must both permit writes. Membership roles and client access remain necessary. Content, messaging, budgets, spend activation, deletion, business administration, identity/access and billing require a durable human approval. Approval binds actor, client, exact canonical plan, authorization revisions, approver membership/revision and expiry. Consumption and PREPARED audit are atomic. The model cannot issue its own approval through an MCP tool.

Ads creates/copies require explicit PAUSED at the root and every nested status. ACTIVE or inherited status is rejected. Budget and activation are separate risks, including inside generic JSON. Complex multi-step clone/bulk operations remain HOLD until every step and created asset is bound to a reviewed plan.

Each mutating permit permits one network attempt. Unknown network or audit-completion outcome is UNKNOWN and requires reconciliation. Audit stores only allowlisted non-sensitive change metadata; before-state evidence is UNKNOWN unless actually observed.

## Human approval

Review and issuance are served at `/platform/approvals` only while `LUMIN_PLATFORM_ENABLED` is true, and answer 403 while `LUMIN_PLATFORM_WRITES_ENABLED` and `AGENCY_WRITES_ENABLED` are not both `true`. The CSRF token is domain separated from other routers that share `SESSION_COOKIE_SECRET`. Separation of duties (`LUMIN_APPROVAL_REQUIRE_DISTINCT_APPROVER`) refuses an approver who is the requesting actor. It is on by default when `DEPLOYMENT_MODE=agency` and both write flags are true and off in other modes. `false` in any case is the only opt-out, `true` forces it on, and any other value (an empty string, `yes`, a padded value) fails closed to on. An MCP credential, an MCP tool and a cross-origin form cannot grant an approval; `tests/platform/approval-http-runtime.test.ts` and `approval-http-production.test.ts` drive the real HTTP runtime for the allowed and refused cases.

Request, review and issue all evaluate policy with the live writes flag (`platformWritesEnabled()`), so with either flag off they deny `DISABLED_BY_LUMIN_POLICY` and store no request, approval or audit record. An approval is consumed exactly once, inside `authorizeOperation`, after policy has been evaluated again.

## Policy guards

`registerPolicyGuard(name, guard)` adds a refusal that runs inside `evaluatePolicy` for every non-READ plan. Because approval request, review/issue and `authorizeOperation` all call `evaluatePolicy`, a guard refuses before a human is asked, before an approval is issued and before one is consumed. A guard can only deny: a throwing guard denies with `POLICY_GUARD_FAILED`, and a name cannot be registered twice by different functions. `tests/platform/policy-guard-before-approval.test.ts` pins request, issue and execution with a stand-in guard. The per-client budget ceiling is registered this way (`budget-ceiling-guard.ts`, configured by `LUMIN_MARKETING_BUDGET_CEILINGS`): an over-ceiling or unconfigured plan is refused when the approval is requested, again when it is reviewed or issued, and once more before the approval is consumed, which leaves the approval unspent (`tests/platform/budget-ceiling-at-approval.test.ts`). The guard also refuses with `MONEY_KEY_UNRECOGNIZED` any money-looking request key that is not an exact name a strict builder emits, because the ceiling can only read exact daily and lifetime budget amounts. `execution.ts` imports the guard module for its exported name, which loads and registers it, so the guard exists however the platform modules are reached, and `authorizeOperation` refuses `POLICY_GUARD_MISSING` before evaluating policy if it is not registered (`tests/platform/policy-guard-registration.test.ts` loads each entry module alone in a fresh module graph).

## Write preparation

A tool that only stages a proposal for a later write is refused while platform writes are disabled, because nothing can approve or run the proposal: `meta_prepare_action` and `meta_prepare_publication` through the approval path, `ads_update_ad_url_tags` and the tracking planner through `legacy-tracking.ts` and the `meta_plan_tracking_change` policy rule, and in agency deployments `ads_update_ad_url_tags` is also not listed. `meta_plan_paused_ads` refuses in the paused ad batch service itself, and agency deployments with writes disabled list none of the five preparation tools (`meta_prepare_action`, `meta_prepare_publication`, `meta_plan_paused_ads`, `meta_plan_ad_tracking_change`, `ads_update_ad_url_tags`). Discovery, observation, targeting lookup, compatibility, owner observation and app promotion access make GET requests only and store evidence or an enrollment proposal; they remain available read-only.

## Mutation inventory

`tests/platform/tool-classification.fixture.ts` classifies all 371 tools the strict build registers: 142 baseline tools (73 read-only agency, 6 read tools kept out of agency, 63 writes of which 32 are approval-gated strict subsets, 1 local review workflow, 1 read replacement and 29 strict holds), 183 product contracts (92 read, 91 mutating with exact operation classes; `marketing_activate_ad` is the only product contract that can start delivery) and 46 control tools. `tests/platform/tool-classification-guard.test.ts` fails when a tool is added without an entry, an entry is stale, `readOnlyHint` disagrees with the class, a baseline-to-strict annotation changes without review, a contract gains or loses a class, a second spend-capable contract appears, or a held write becomes executable. It also asserts the tools a read-only agency deployment enables.

## Unreconciled attempts

An operation that finishes UNKNOWN or PARTIAL never changes state, and a provider write may have happened. `prepareOperation` therefore writes a per-(tenant, plan hash) lock in the same transaction as the operation and audit in both repositories, and refuses `PRIOR_ATTEMPT_UNRECONCILED` while one is held. Only a SUCCEEDED or FAILED finish by the holding operation releases it; UNKNOWN, PARTIAL and an operation that never finished (a crash after prepare) keep it. The check runs after the approval checks and before any write, so an approval refused by the lock stays unspent, and approval request, review and issue refuse the same way before a human is asked. A changed plan is a different hash and is not blocked, so a deliberate retry after reconciling by hand changes the plan. There is no automatic release: a locked plan stays locked until an operator-driven reconciliation path exists. `tests/platform/plan-lock.test.ts` (both repositories, including the Firestore race), `plan-lock-authorization.test.ts` and `duplicate-write-after-unknown.test.ts` pin the behaviour. The lock key is the hash of what is sent, not of the whole plan: `planLockHash` drops `targeting_lookup_ids` and `targeting_lookup_selected`, the read-only lookup evidence, so re-running a lookup (which needs no approval) cannot unlock an ad set whose create ended UNKNOWN. Approvals stay bound to the full plan hash, so a human still approves the evidence itself (`tests/platform/targeting-lookup.test.ts`). The lock row holds only its hashed key, tenant, operation id, state and timestamps. It names no actor, client or tool, so there is nothing in it for a Meta data-deletion request to erase (`tests/platform/plan-lock-privacy.test.ts`).

A failure frees the plan only when it cannot have reached Meta. An operation finishes FAILED, which releases the lock, when the single mutation step was never begun (a read failed first, validation or a local exception) or when Meta provably rejected the request: a 4xx with a Graph error code that is not transient, not code 1 or 2, and not 408 or 429 (`src/platform/failure-outcome.ts`). Once the step has begun, a timeout, a lost connection, a 5xx, a throttle or a response that cannot be read stays UNKNOWN and keeps the lock until it is reconciled. Product clients other than the generic Graph client report any non-success after the step as an unknown outcome, so a rejection by one of them also keeps the lock; only the generic client and the legacy write path tell a refusal apart. A throttled write (429) is UNKNOWN on purpose. `tests/platform/failure-outcome.test.ts`, `duplicate-write-after-unknown.test.ts` and `budget-ceiling-at-approval.test.ts` pin both outcomes.

Lock rows are never deleted: there is one document per distinct mutating plan per tenant, and no TTL is configured on `operationPlanLocks` because an expired lock would silently reopen a plan whose write may have happened. Retention is an open decision. Locks start at the release that introduced them, so operations already UNKNOWN, PARTIAL or PREPARED before then have no lock; see the rollout step in `docs/operations.md`.

## Money-looking keys

`classifyPlan` marks a plan WRITE_BUDGET when any key at any depth, including inside JSON-encoded strings, matches `budget`, `spend_cap`, `spend_target`, `spend_limit` or `bid_` after case folding and after removing spaces, zero-width characters and bracket syntax. The only exempt keys are the four `expected_*` activation expectations of `marketing_activate_ad`. An ACTIVE status is recognised at any depth the plan allows. Defence in depth: no current builder emits the extra spellings (`tests/platform/money-key-classification.test.ts`). A string that starts with `[` or `{` is decoded and inspected only if it parses as JSON. One that does not parse (`[New] Summer sale`, `{{product.name}} on sale`) is plain text, as it is to Graph, and is neither refused nor read for keys; the ceiling walker reads it the same way (`tests/platform/bracketed-text-values.test.ts`).

## Writes that need no human approval

Only the classes in `HUMAN_APPROVAL_CLASSES` and the tool `signals_send_crm_lead_event` need an approval. WRITE_NON_FINANCIAL is not among them, so `signals_send_pixel_events` sends its Meta Conversions API POST with no approval request, review or consumption when both write flags are true (G2-03). It sends one stored, consented first-party event by references only and is denied with `DISABLED_BY_LUMIN_POLICY` unless both flags are on, and the tool does not exist when the platform is off (`tests/platform/signals-pixel-writes.test.ts`). This is a recorded exemption, pinned by `PRODUCT_WRITES_WITHOUT_HUMAN_APPROVAL` in the classification fixture. An agency that wants the strict "every write has a one-use human approval" invariant for this class must have an `approval_id` threaded through the tool before it enables platform writes; that is an owner decision.

## What the approval page says

The page shows the exact plan. A typed update always sends `status=PAUSED` with its other fields, so approving a budget or name change on a live campaign, ad set or ad pauses it; the page says so in plain language for non-create plans whose provider body status is PAUSED. It shows raw minor-unit amounts without a currency (G2-08, deferred), and ceilings are per entity, not an aggregate per account or client.

## Account ownership

Account mutations (ad configuration, budget, activation, uploads, audiences, conversions, reports, rules, studies) need a current owner billing attestation and a provider ownership observation that is at most five minutes old. An account that staging `1f08563` reassociated carries neither: it stays readable and every account mutation denies `ACCOUNT_OWNERSHIP_UNVERIFIED` until fresh evidence exists, and again once the observation is older than its window (`tests/platform/account-ownership-reassociated.test.ts`). The decisions that differ from staging are pinned in `tests/platform/policy-staging-delta.test.ts`.
